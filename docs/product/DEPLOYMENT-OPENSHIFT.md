# OpenShift / IBM Marketplace deployment

Chariot's `chariot-gateway` container image and Helm chart, adapted for the
Red Hat OpenShift / IBM Marketplace certification track. This is a companion
to the AWS Marketplace path (`.github/workflows/marketplace-ecr.yml`,
`helm/chariot/values-airgap.yaml`) — the image and chart are the same
artifacts; this document covers what differs for OpenShift.

## Certification checklist

Red Hat's container-certification policy guide (docs.redhat.com, fetched
2026-09-03), quoted verbatim, mapped to what this chart/image does:

| Requirement (verbatim) | This repo |
|---|---|
| "Container images must use a Universal Base Image (UBI) provided by Red Hat." | `Dockerfile`'s `BASE_IMAGE` ARG defaults to `registry.access.redhat.com/ubi9/nodejs-22-minimal:9.8-1788225630@sha256:afb61551cc2872c2c6ad54b610a3cf05372404c0ac8e2c9d1ab9627242b1d15d` — pinned by an immutable Red Hat catalog tag plus its manifest digest (verified live against the Red Hat Ecosystem Catalog API on 2026-09-03), not the floating `9.8`/`latest` tags. Still glibc (RHEL userspace), so the napi addon (built for `x86_64-unknown-linux-gnu`) loads unchanged — same reasoning that ruled out Alpine before this change. |
| "Container images must declare a non-root user unless their functionality requires privileged access." | `Dockerfile`'s runtime stage still ends in `USER 1000:1000` (unchanged numeric UID) after a `chown -R 1000:1000` block that no longer depends on a named `node` OS user — the UBI9 base defines no such name, only a numeric default (`USER 1001`), so the chown is numeric on both the UBI default and the Debian override. |
| "Container images must have a `/licenses` directory." | Already shipped (`Dockerfile`: `COPY LICENSE-ELASTIC THIRD-PARTY-NOTICES.md /licenses/`, generated by `scripts/generate-third-party-notices.mjs`) by a parallel change in this release wave — this document only records that it exists; the ownership fix below (`chown -R 1000:1000 /app /licenses ...`) had to account for it once it landed. |
| "Container images must include the following labels: name, maintainer, vendor, version, release, summary, description." | Added to the runtime stage's `LABEL` block alongside the existing `org.opencontainers.image.*` set. `vendor`/`name`/`maintainer` are protectNIL's own values, not a Red Hat trademark, satisfying the adjacent "must not begin with a Red Hat trademark" clause. `release` is a new `CHARIOT_RELEASE` build arg (default `1`), distinct from `CHARIOT_VERSION` — it increments on a same-version rebuild (e.g. a base-image CVE respin), the version does not. |
| "Uncompressed container images must have less than 40 layers." | The UBI9 `nodejs-22-minimal` base itself is 2 layers (verified live via the Red Hat Ecosystem Catalog API). The runtime stage adds 15 more (`RUN`/`COPY` instructions only — `LABEL`/`ENV`/`WORKDIR`/`ARG`/`USER`/`EXPOSE`/`VOLUME`/`HEALTHCHECK`/`ENTRYPOINT` are metadata, not layers; this includes the `/licenses` COPY), for **17 uncompressed layers total** — well under the 40 limit. `.github/workflows/marketplace-ecr.yml` now asserts this at build time (`docker inspect --format '{{ len .RootFS.Layers }}'` on the just-pushed digest) so a future change that pushes the count over budget fails the pipeline, not certification. |
| "Container images must not contain Red Hat components with identified important or critical vulnerabilities." | Not something this repo can assert at build time — it depends on what CVEs are open against the pinned base image on the day of a given build. Follow-up: wire a scan (e.g. `docker scout` / Clair / the RHACS instance itself, see below) into the release pipeline as a gate; **not done in this change** — flagging it rather than silently leaving it uncovered. |

## SCC posture

The gateway's pod/container security context (`helm/chariot/values.yaml`)
deliberately leaves `runAsUser`/`runAsGroup`/`fsGroup` **unset**. OpenShift's
default `restricted-v2` SCC uses the `MustRunAsRange` strategy: it allocates
the UID from the project's `openshift.io/sa.scc.uid-range` annotation and the
supplemental group from `.../supplemental-groups`, mutating the pod before
admission. A hardcoded `1000` (or the image's own default) falls outside every
realistic per-namespace range, so pinning it would force a buyer into a
cluster-admin SCC grant (`nonroot-v2`/`anyuid`) — itself a certification
finding. See the extended comments already in `helm/chariot/values.yaml`
(`podSecurityContext`/`securityContext`) and `values-openshift.yaml` for the
full reasoning, including why the vendored `mongodb`/`redis` subcharts (which
run root-by-default upstream images) need `openshift.arbitraryUid: true` while
the gateway — whose own image declares `USER 1000:1000` and ships group-0
writable `/app` + the runtime volume — does not.

`fsGroup` is what matters most for the SCC-injected identity to actually
*write* the persistent volume; leaving it unset lets the SCC supply a group
consistent with whatever UID it injected, rather than a group the injected UID
isn't in.

## RHACS vs Kyverno

The chart's CH-54 deploy-time image-signature verification now has a
`helm/chariot/values.yaml` `imageVerification.engine` switch:

- `kyverno` (default) — unchanged from before this change. Renders the
  `kyverno.io/v1` `ClusterPolicy` in `helm/chariot/templates/image-verify-policy.yaml`.
  This is the EKS-era default and stays the default so existing EKS installs
  render identically.
- `rhacs` — the certified verifier for the OpenShift / IBM Marketplace
  channel. **RHACS (Red Hat Advanced Cluster Security) has no
  Helm-renderable CRD** for either the trust material (`SignatureIntegration`)
  or the enforcement policy that references it — both are owned by RHACS
  Central as REST resources (Central UI, Central API, or `roxctl`), not
  Kubernetes custom resources, per Red Hat Advanced Cluster Security for
  Kubernetes's own docs ("Operating > Verifying image signatures"). So this
  engine instead renders a `ConfigMap`
  (`helm/chariot/templates/rhacs-signature-integration-note.yaml`) carrying
  the exact `roxctl central signature-integrations create` invocation and the
  JSON payload an operator (or a CI step with Central API access) submits to
  reproduce, in RHACS, what the Kyverno engine enforces automatically on EKS.
  Also note: RHACS re-verifies signatures on a fixed interval (Central docs:
  every 4 hours) rather than per-admission-request the way the Kyverno
  webhook does — a different enforcement latency model, not a weaker one.
- `none` — no verifier renders. Refused by `chariot.assertImageVerifyFailClosed`
  (`helm/chariot/templates/_helpers.tpl`) unless
  `imageVerification.allowInsecureAdmissionMode=true` is set explicitly. That
  helper is now called **unconditionally** from both
  `image-verify-policy.yaml` and `rhacs-signature-integration-note.yaml` (not
  nested inside the `if` that gates whether either resource renders), closing
  a prior gap where `imageVerification.enabled: false` alone skipped the
  fail-closed check along with the policy it would have guarded.

`values-openshift.yaml` sets `imageVerification.engine: rhacs` (alongside its
existing `mongodb.openshift.arbitraryUid` / `redis.openshift.arbitraryUid`
settings). It deliberately leaves `imageVerification.rhacs.signatureIntegrationName`
and `.enforcementPolicyName` for the operator to fill in — they name resources
created in the buyer's own RHACS Central, which this repo has no access to.

## Install command

```
helm install chariot ./helm/chariot \
  -f values-openshift.yaml \
  --set gateway.existingSecret=<your-secret-name> \
  --set mongodb.auth.rootPassword=<or use an existingSecret> \
  --set redis.auth.password=<or use an existingSecret> \
  --set imageVerification.rhacs.signatureIntegrationName=<name-you-created-in-Central> \
  --set imageVerification.rhacs.enforcementPolicyName=<name-you-created-in-Central> \
  -f <your-values>.yaml
```

`gateway.existingSecret`, `mongodb.auth.rootPassword`/`redis.auth.password`
(or their `existingSecret` equivalents) are required regardless of platform —
see the CH-28 fail-closed checks in `helm/chariot/templates/_helpers.tpl`;
they are not OpenShift-specific.

## What this change did NOT do

The Dockerfile/Helm/CI changes in this document were verified without a
container build: `bash -n` on the workflow's shell blocks, YAML parsing of every
changed YAML file, and `helm lint` plus `helm template` executed with a
downloaded `helm` v3.16.3 binary (helm is not installed on the authoring host)
against all three `imageVerification.engine` values (`kyverno`, `rhacs` with
and without required names set, `none` with and without the break-glass flag)
plus the `-f values-openshift.yaml` overlay. **No container image was built** (`docker`/`podman` are not
installed on the host this change was authored on) and **no admission run
against a real OpenShift cluster (RHACS or otherwise) has been performed.**
Both are OPERATOR steps, not yet done — this document describes what to run,
it does not claim the run happened.
